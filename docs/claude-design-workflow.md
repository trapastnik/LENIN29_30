# Работа с Claude Design

Документ описывает, как продолжать использовать Claude Design в проекте МТК 29 без превращения кодовой базы в набор несвязанных дизайн-экспортов.

## Контекст

Проект сейчас гибридный:

```text
/src + parties.html + states.html + brand.html
→ Vite + Vanilla JS + Web Components

/public/expo/
→ импортированный Claude Design-прототип: React + Babel в браузере
```

Такой гибрид допустим для прототипа. Claude Design быстро даёт визуальные проходы, композиции и анимационные сцены; Vite-проект удерживает навигацию, данные, общие стили, сборку и интеграцию.

Главное правило: Claude Design остаётся мастерской для быстрых визуальных итераций, а рабочий проект остаётся местом, куда попадает уже адаптированный код.

## Что Делать В Claude Design

Claude Design хорошо подходит для:

- новых экранов и визуальных вариантов;
- сложных композиций;
- кинематографичных сцен;
- быстрых интерактивных прототипов;
- поиска атмосферы и ритма;
- отдельных компонентов, которые потом можно перенести в проект.

Не стоит просить Claude Design заново делать:

- общую навигацию проекта;
- PIN-gate;
- переключение языка;
- iframe/postMessage-интеграцию;
- структуру контентных JSON;
- роутинг;
- правила сборки;
- загрузку общих данных.

Эти вещи должны оставаться в кодовой базе, иначе каждый новый импорт начнёт ломать уже принятые проектные решения.

## Куда Класть Импорты

Сырой экспорт из Claude Design не нужно сразу вставлять в рабочие страницы. Для него стоит использовать отдельную зону:

```text
src/design-lab/
```

Рекомендуемый формат:

```text
src/design-lab/2026-04-28-front-map/
├── README.md
├── index.html
├── component.jsx
├── styles.css
├── data-shape.json
└── assets/
```

Если экспорт временно удобнее держать как статический набор файлов, допустим вариант:

```text
public/design-imports/
```

Но рабочий путь всё равно должен быть таким:

```text
Claude Design export
→ design-lab / design-imports
→ адаптация под проект
→ подключение к Vite/странице
→ smoke-проверка
→ перенос в рабочий раздел
```

## README Для Каждого Импорта

Каждый импорт должен сопровождаться коротким `README.md`.

Шаблон:

```md
# Claude Design import: front-map

Дата: 2026-04-28
Цель: новый экран карты фронтов
Статус: сырой прототип

Что нужно перенести:
- композиция
- анимация временной шкалы
- карточки событий

Что нельзя переносить напрямую:
- CDN React/Babel
- inline demo data
- случайные пути к ассетам
- самостоятельный router/header/PIN

Зависимости:
- ожидает данные в формате ...
- использует ассеты ...
```

Такой README помогает отделить художественную находку от технического мусора, который часто появляется в генеративном прототипе.

## Как Формулировать Задачи Для Claude Design

Перед новым проходом полезно давать Claude Design ограничения проекта:

```text
Проект: музейная интерактивная экспозиция.
Экран: 1920x1080, touch kiosk.
Стиль: использовать существующие цвета brass/paper/ink/red.
Код будет встроен в Vite-проект.
Не использовать внешние CDN.
Не делать router, header, PIN, language switch.
Данные будут приходить из JSON.
Сделать изолированный экран/компонент.
```

Лучше просить не "сайт целиком", а конкретный модуль:

```text
Сделай экран выбора события для раздела "Государственные образования".
Он будет встроен внутрь существующего проекта.
Не делай общую навигацию.
Не придумывай новые глобальные стили.
Не подключай внешние библиотеки через CDN.
```

## Лучший Формат Результата

Предпочтительный экспорт:

```text
Component.jsx
styles.css
assets/
data-shape.json
integration-notes.md
```

Нежелательный экспорт:

```text
один огромный HTML
inline data
inline styles на всё
CDN-зависимости
самодельная навигация
```

Если Claude Design всё равно отдаёт большой HTML, его нужно считать сырьём, а не финальным кодом.

## Правила Адаптации

Перед переносом в рабочий проект нужно проверить:

- какие части являются визуальным решением, а какие просто технической обвязкой прототипа;
- какие данные нужно заменить на JSON из `public/content/`;
- какие стили можно привязать к `src/styles/tokens.css`;
- есть ли CDN-зависимости;
- есть ли глобальные обработчики клавиатуры/scroll/resize;
- не конфликтуют ли имена `localStorage`/`sessionStorage` ключей;
- не ломается ли прямой заход на страницу;
- не ломается ли режим iframe-оверлея внутри `/expo/`.

Все общие механики должны оставаться проектными:

- PIN-gate;
- язык `expo:lang`;
- back-link;
- открытие/закрытие разделов;
- `postMessage('mtk29:close-section')`;
- пути к контенту;
- общие токены и шрифты.

## Стратегия Для Текущего Проекта

На ближайший этап лучше не переписывать всё сразу. Практичный порядок:

1. Зафиксировать текущую гибридную архитектуру.
2. Стабилизировать PIN, навигацию, iframe-режимы и прямой заход на страницы.
3. Оставить Claude Design как источник новых визуальных проходов.
4. Сырые импорты складывать в `src/design-lab/`.
5. Переносить в рабочие разделы только после адаптации.
6. Постепенно убирать самые хрупкие места: CDN, Babel in-browser, случайные inline-данные.
7. Позже перевести `/public/expo/` под Vite-сборку или явно оставить его как отдельную React-сцену с документированными границами.

## Smoke-Чеклист После Импорта

Минимальная проверка:

```bash
npm run build
npm run preview
```

В браузере:

- `/expo/` открывается;
- PIN-gate работает;
- кнопка "К персоналиям" работает без PIN;
- `/parties.html` открывается напрямую;
- `/states.html` открывается напрямую;
- `parties` и `states` открываются как iframe-оверлеи из `/expo/`;
- back-link закрывает iframe-оверлей;
- язык не сбрасывается неожиданно;
- в консоли нет ошибок;
- на целевом размере 1920x1080 нет наложений текста и кнопок.

## Итог

Claude Design можно и нужно продолжать использовать, но как дизайн-лабораторию. Основной проект должен принимать из него не весь экспорт целиком, а очищенные решения: композицию, анимацию, ассеты и отдельные компоненты, приведённые к правилам проекта.
